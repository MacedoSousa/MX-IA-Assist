# MX prototype local semantic RAG

## Delivered scope

The study context now combines existing lexical ranking with **local embeddings** generated by Ollama. The implementation uses `nomic-embed-text` through local `/api/embed`, retains an in-memory vector index per process, and adds a cosine-similarity score to the lexical score to rerank eligible chunks. Ollama supports batch vector generation and recommends cosine similarity for semantic retrieval.[1]

| Layer | Behaviour |
|---|---|
| Shared authorized source | Imported chunks without an `owner` field receive the `shared-authorized` scope. |
| Runtime external evidence | Receives the owner UUID; other users cannot retrieve or cite it. |
| Ranking | Controlled lexical score plus semantic score; embedding failure falls back to lexical ranking without interrupting chat. |
| Vectors | In-memory cache by chunk ID. Vectors and prompt text are never logged. |
| Citations | Preserve source, origin, heading, chunk, SHA-256, and honest page indication. |
| Embedding model | `nomic-embed-text`, locally installed in Docker Ollama and validated with one 768-dimension vector. |

## Explicit boundaries

This increment does not create a persistent vector database and does not modify the authorized corpus. The index rebuilds after Core restarts; this keeps the prototype simple and avoids storing user-question/evidence vectors without an approved retention policy. The next step must assess owner-scoped persistence, embedding version, auditable reindexing, and relevance metrics before introducing a vector database.

Lexical fallback remains mandatory: local endpoint unavailability, an invalid response, or incompatible dimensions do not crash chat or trigger external search beyond the existing coverage rules.

## Evidence

`scripts/validate-ollama-embeddings.py` confirmed the local endpoint and a 768-dimension vector without printing the vector. Core tests cover similarity retrieval without lexical overlap and deny one owner's runtime external evidence to another owner.
